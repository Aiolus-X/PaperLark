# PaperLark 执行模型

## 一条评论如何变成回答

1. 飞书评论通知或轮询发现新回复，以文件 Token＋评论 ID＋回复 ID 去重。
2. 判断指令；非指令仅在当前线程已有机器人回答时视为追问。只处理可访问的文档。
3. Docx 从官方 `quote` 获取选区；PDF 从扩展按同一评论 ID 关联精确原文。引用尚未到达时等待，不猜选区。
4. 按任务组装上下文，调用模型，完整生成后再向同一飞书评论线程回复。
5. 写文档的任务先保存草稿，再创建/写入目标文档，保留明确失败阶段。

## 上传与缓存

- `/trans` 没有额外范围时，只传选中原文和必要标题信息，不下载/上传全文。
- `/ask`、`/think` 使用全文＋选区＋当前线程最近 12 条、最多 30,000 字符的讨论。当前支持的文档规模直接传全文，没有声称实现检索式裁剪。
- `/sum`、`/doc`、`/key`、`/highlight` 根据全文工作；`/compare` 会读取双方正文。
- 服务缓存已解析正文：Docx 用 revision，PDF 用最后修改时间判断是否变化。每次仍检查版本/权限，但相同版本不会重复下载和解析。
- **本地缓存不等于模型记忆**：多数模型请求是独立的，仍需将本次需要的文档文字和历史作为输入；`store:false` 不依赖模型服务替我们保存会话。
- `/doc` 的失败重试可复用同内容＋模板＋要求生成的草稿；`--refresh` 强制重新生成。

## 并发与状态

- 默认最多三个任务同时调用模型，可用 `PAPERLARK_MAX_CONCURRENT_JOBS` 配置。
- 同一评论线程保持顺序，等待 PDF 引用时，后续回复也不会超车。
- 不同线程可并发；同一文档的 `/doc`、`/add`、`/note`、`/highlight` 写操作额外串行，避免互相覆盖。
- 重复通知/轮询不会重复回答。普通评论和机器人自身回复会被忽略。
- 最近同一线程的 AI 回答参与后续讨论；不会把其他文档或其他评论线程拼进历史。
- 任务及关联保存在 `data/state.json`。当前是单实例服务，不支持多个进程同时写同一个状态文件。

## 自动接入

扩展 0.2.2 会在打开已授权的 Docx/PDF/Wiki 时登记文档，并在路由变化时跟随切换。官方接口校验访问权限；无法访问时在扩展状态里显示错误。首次接入仅补处理最近 24 小时尚未回答的 `/ask`、`/trans`、`/think`，不重放历史写操作。PDF 高亮面板会区分已保存、已匹配和当前可见状态。

收到某篇新文档的评论事件也会尝试自动登记。纯桌面客户端从未在服务登记的新文档，不能保证只添加应用后立即发现；飞书评论事件是通知视角，不是所有可访问文档的全量广播。

## 输出风格

默认结论先行、简洁、高信息密度。普通问答/讨论约 150–350 中文字以内，简单问题更短；`/doc` 默认约 800–1200 字，保持 TL;DR、Motivation、Method、Main Result、思考结构。完整翻译、用户明确要求的推导或长文不受这个默认长度约束。

模型由本机配置决定，可在 `/app` 设置页切换。Responses 使用流式接收并记录生成进度，只有完整结果才会写入；普通任务默认 180 秒，文档任务默认 600 秒，可通过 `LLM_TIMEOUT_MS` / `LLM_DOCUMENT_TIMEOUT_MS` 调整。
