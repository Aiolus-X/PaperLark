# 添加应用与分享权限

## 为什么添加后不一定立即回复

添加 PaperLark 授予应用对该文档的访问权限；它不等于飞书会向应用推送该文档每条普通评论。官方 `drive.notice.comment_add_v1` 遵循接收者通知规则。

当前网页方案：安装扩展 0.2.2 后，打开有权限的文档自动登记，再通过评论通知和轮询处理新指令。PDF 扩展还提供精确引用；普通 Docx 使用官方评论引用。服务保持在线即可，浏览器内不需要手动配置每篇文档。纯桌面里未登记的新文档仍需先用网页打开或产生应用能收到的评论通知。

## 他人的文档

- 添加文档应用的操作者通常需要文档管理权限，或知识库管理员身份。
- 应用已发布，具有云文档 API 权限，可用范围应包含文档所有者；否则文档应用搜索可能找不到 PaperLark。
- 文档、PDF 下载、知识库父节点等资源权限要按对应动作分别具备。自己能读文档，不等于应用已获权限。
- 当前普通 Docx 指令不限制为开发者本人；PDF 精确引用的本机桥接仍按配对阅读者验证作者。让另一个阅读者用 PDF 扩展，需要独立配对/部署，尚不是多租户商用产品。
- 不同企业之间的自建应用可用范围和外部文档策略需要由管理员/平台确认，不承诺当前私有应用跨租户即装即用。

## `/doc` 的权限阶段

1. 读取论文正文和分享模板：文档阅读权限。
2. 在知识库创建同级总结：应用身份 `wiki:node:create`（或更宽的 `wiki:wiki`），以及目标父节点/知识空间的创建权限。
3. 写入总结块和 ToDo：`docx:document`，并有新文档编辑权限。

只申请当前实际缺失的权限。修改应用权限后需要发布并完成管理员审批（如有）。2026-10-26 的真实错误为第 2 步缺 `wiki:node:create`；原模板指定版本读取被拒的问题已通过代码改为最新内容读取修复。

后续用户开通并发布后，节点创建 API 权限已通过；新的错误为 `131006 wiki space permission denied, tenant needs edit permission`。这表示具体知识空间没有给应用编辑权限，不应继续扩大 API scope 来碰运气。

保持同目录的授权方式：创建包含 PaperLark **应用机器人**的专用群，知识库管理员在“知识库设置 → 成员设置”把该群加入**可编辑成员**。不必给管理员权限。若采用小范围授权，可建立一个总结父页面，给 PaperLark 该节点的编辑权限，然后使用 `/doc --path <父页面链接>`。

API 权限和资源权限是两层。若原论文位于知识空间根目录，默认同目录创建需要空间编辑权限；只把应用添加到 PDF 本身并不授予父空间编辑权限。移动论文后服务会重新读取当前父节点，不沿用旧位置缓存。
