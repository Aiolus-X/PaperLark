# 飞书文档应用开发

围绕用户实际要完成的文档操作推进。先判断入口是 Docx、知识库节点还是上传文件，再确认调用身份、事件来源及输出位置。复用项目现有实现；不要把一次项目里的模型、目录、扩展或部署方式强加给其他任务。

## 快速定位

- **不触发、漏评论、线程上下文错误或 PDF 引用不准**：读 [评论与 PDF](references/comments-and-pdf.md)。
- **forbidden、permission denied、知识库创建或 Docx 写入失败**：读 [权限与文档](references/permissions-and-documents.md)。
- 普通实现先查现有配置、入口和测试。只有缺少关键事实时才询问用户；不让用户重复授予已经生效的权限。

## 关键决策

1. 将应用 API scope、应用使用范围、具体文档/父节点权限分开检查。应用鉴权成功或用户本人能访问文档，都不证明应用能执行目标操作。
2. 知识库 URL 的节点 Token 不等于实际文档 Token。解析节点后使用返回的对象类型与 Token；创建同级节点还要知道当前父节点。
3. 评论通知不是所有可访问文档评论的广播。若产品要求“打开即用”，明确实现自动登记/发现；不能用固定监控名单冒充通用接入。
4. PDF 页码占位符不是选中文字。没有取得准确原文时，不调用模型假装翻译选区，也不静默改成翻译整页。
5. 每次 AI 调用显式构造需要的正文、引用和线程历史。正文缓存解决下载与解析成本，不等于模型具有持久记忆。
6. 区分任务入队、模型生成、远程写入和回复投递。写入部分成功或响应不确定时，先检查实际文档；不自动重复创建文档或发送评论。

## 操作与验证

- 配置中的 App Secret、模型 Key、会话 Cookie 和配对凭据留在私有存储；日志、测试样例和 skill 中只用虚构标识。
- 调试真实任务时使用它的文件、评论和回复 ID 关联证据；按机器人身份判断自身回复，不能仅靠文本前缀。
- 对已有授权的任务直接完成必要操作。用于测试的额外外部消息或写入，需要处于用户已授权范围；没有授权时使用隔离替身。不要把同意修 bug 解释为可以扩大部署、发布或账号权限。
- 对权限错误记录失败阶段和错误码，补最小缺口。对限流可退避；对可能已执行的写操作不做盲重试。
- 将代码实现、隔离测试和真实租户验收分别记录。显示功能须核对真实可见结果；“生成了建议”或“保存了引用”不等于渲染成功。
- 在不影响其他任务的前提下保持服务在线；需要重启时先确认没有正在写入的任务，停止旧进程后再启动新进程，避免两个单实例写同一状态文件。

## 查阅官方接口

优先使用实际安装 SDK 的接口定义与当前飞书官方文档确认请求字段、权限和返回值。官方页面无法解析时，可尝试在对应文档 URL 后加 `.md` 获取纯文本；若仍无法读取，说明验证限制。前端内部请求结构应标为观察到的兼容实现，不称为官方开放接口。

Skill 中的故障案例帮助提出假设，不代替当前项目的证据。部署环境、发布操作和账号凭据应由项目配置提供，不写死到 skill。
